# Phase 4 implementation and acceptance

The staff AI Integration navigation and provider/model admin screens are implemented. Platform ownership is distinct from club director membership and is never inferred automatically. Owner configuration additionally requires an eligible club manager membership and MFA. Synthetic inference testing checks a fixed JSON marker, not a model-list endpoint. Credentials can reference server environment secrets or be AES-256-GCM encrypted with a server root key, random nonce and provider-specific authenticated data. Key changes require an existing MFA session plus a fresh server password check. Only the restricted server database role can store/read encrypted credentials; browser sessions cannot select the credential table or execute those functions. No raw key, prompt, response or provider error body is stored in attempt telemetry.

The independent router implements provider priority, ordered model fallbacks, purpose/privacy checks, allowlisted HTTPS origins, redirect rejection, token/context limits, bounded timeouts/attempts/output, JSON/Zod validation, 401/403 configuration faults, 429 cooldown/failover, transient fallback, persistent circuit state, conservative monthly club/role and request budget reservations, and per-actor request limits. Failed/interrupted reservations remain charged to the conservative budget; measured token-cost estimates are separate. Prices are explicit configuration, never assumed current vendor prices. Vision is deliberately unavailable until an image adapter is implemented, even if a model is labeled vision-capable.

The read-only staff assistant retrieves only the selected approved club rule version and validates returned citation IDs against those retrieved excerpts. It has no domain mutation tools. Participant records, reasons and private notes are excluded. A user explicitly confirms sending their question and excerpts; no raw chat history is persisted. Missing approved sources, disabled configuration, absent credentials or exhausted budgets fail closed. Source/question instructions are treated as untrusted data. Citation membership validation is not proof of semantic factual accuracy; manual/evaluation review remains necessary.

Migrations 017–018 are applied to staging without seeds. Runtime role provisioning creates a dedicated database login with no table access, named function grants and a connection limit; its URL and root encryption key stay in ignored .env.local. Deployments need managed secret storage, TLS/network verification and independent rotation/restore procedures. Platform Owner assignment is pending the user's answer; no provider has been configured or enabled and no live inference/spend has been performed.

Human event proposals are now implemented and migration 019 is applied. A human reviews exact scope/payload and approves creation of a private calendar draft; publication remains a separate action. Three SQL cases cover role/tenant denial, edited-payload rejection, reviewer attribution, idempotency and zero published events. Hosted verification confirmed the AI runtime login has no SELECT privilege on participant or credential tables.

Outstanding Phase 4 acceptance/features: task/message/recognition proposal types; SQL analytics summarization; richer curated corpus/retrieval; PDF OCR/vision/AI integration; provider-specific live inference and timeout/rate-limit fixtures; authenticated owner/mentor UI visual and accessibility verification; global aggregate budget/rate controls; secret backup/key rotation drill; native PostgreSQL concurrency testing. The admin role's own direct accounting RPCs remain trusted administrative operations; ordinary staff accounting is available only through the verified server runtime.

Development proceeds without a phase permission gate. The app is not yet production-ready.
