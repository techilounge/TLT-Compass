## AI module acceptance checklist

Every item below is missing. It must be implemented as a functional module, not a placeholder providers page.

- Provider registry: configurable priority/reorder, enable/disable, provider type, allowed base URLs, encrypted server-only secret references, privileged reauthentication and audited key updates. Club directors must not automatically receive global platform-owner privileges.
- Model/route registry: models editable without redeployment, capabilities/privacy approvals, default and fallback models, purposes assistant_chat/calendar_extract/question_generation/summarization/vision, versioned optional pricing.
- Adapters: OpenRouter, OpenAI-compatible, Anthropic and Gemini behind domain-independent interfaces; provider egress allowlists and SSRF defenses for configurable endpoints.
- Routing: token/cost/time limits, bounded retries, model then provider failover, persistent circuit state, configuration faults for 401/403, 429 backoff, bounded 5xx/timeout handling and task-specific Zod output checks.
- Administration: synthetic inference Test, redacted credential/capability/quota/permission errors, checked-at timestamps, latency/usage/cost/correlation IDs, tenant/role/month budgets and emergency AI-off. A successful model-list response is not an inference health check.
- Assistant: staff-only, source-linked versioned retrieval; uncertain policy claims remain uncertain. Authoritative metrics come from SQL/API, not model arithmetic.
- Writes: exact scoped proposal cards with authorized human approval and audit; no autonomous role changes, safeguarding judgments, official completion, points awards or calendar publication. Core app works with AI disabled.
- Acceptance: Gemini 403 PERMISSION_DENIED fixture, invalid credentials, quota/rate limits, timeouts, invalid JSON, exhausted fallbacks, spend cap and prompt-injection tests; zero-autonomous-write gate.

## Architecture and product deviations

1. Platform Owner/Super Admin role is absent; the club-role enum contains director, coordinator, primary mentor, operational mentor and participant. Platform credential administration needs its own authority model.
2. UI is a combined workspace plus administration page, not the blueprint's role-specific screen/navigation set. Participants do not yet get the full specified milestones/attendance/hours/points dashboard.
3. Current server actions/RPCs provide transactional domain boundaries but do not implement the proposed external HTTP API surface. TanStack Query and React Hook Form are not installed; server actions/native forms are the current implementation. These stack choices should be documented, not counted as completed blueprint dependencies.
4. Schema is intentionally a subset: no attendance, hours, level reviews, points, calendar/imports, AI, notifications, exports, retention or separately restricted safeguarding tables. Department codes are typed values, not a departments catalog table.
5. Timezone behavior follows the user's clarification: instants display in the browser timezone; club program dates use its configurable timezone. Existing season dates remain date-only.
6. Curriculum sources are not verified. Never describe operator-entered drafts or synthetic fixtures as official catalog coverage.
7. Only the initial staging Supabase project is provisioned. Localhost is the frontend; separate production infrastructure and deployment are absent.
8. Source status documents had stale claims about unprovisioned staging/unverified MFA. Their current summaries are corrected with this audit. Historical entries remain explicitly historical.
